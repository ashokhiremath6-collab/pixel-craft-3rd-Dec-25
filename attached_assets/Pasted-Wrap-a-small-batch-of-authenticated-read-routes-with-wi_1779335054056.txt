Wrap a small batch of authenticated read routes with withRequestOrg, following the same pattern proven on /api/auth/user in the last session.

The middleware is purely additive: it opens a transaction and sets app.current_org_id from req.user.orgId. It does NOT yet enforce filtering — no RLS policy reads the variable yet. So this session's risk is low: the worst plausible outcome is a route slowed slightly by transaction overhead, not a data error.
